Objetivo: criar uma operação única em que catálogo, estoque, locações, agenda, imagens e agente de IA compartilhem a mesma fonte de dados.

0. Visão executiva

O sistema será desenhado como uma plataforma de gestão de locação de decoração e terá a Magia Festeira como primeira operação. A estrutura deve nascer preparada para futuramente atender outras empresas, mas sem misturar os dados da Magia com terceiros.

Recomendação-chave: não usar o PostgreSQL do HostGator como segundo banco principal. O sistema deve ter um PostgreSQL primário no Supabase. O HostGator pode continuar hospedando outros componentes, mas duplicar a base operacional aumentaria risco de divergência, sincronização e manutenção.

1. Requisitos consolidados

Acervo inicial com mais de 100 temas e possibilidade de crescimento para milhares de registros.

Cada tema pode possuir múltiplas fotos e uma foto principal.

Estrutura hierárquica: tema principal -&gt; variações -&gt; kits -&gt; itens/opcionais.

Suporte a itens avulsos com estoque próprio e reutilizáveis em diferentes temas.

Campos mínimos: categoria, personagens, quantidade de peças, valor, descrição, observações e código interno.

Código único por registro, com numeração controlada e sem colisões.

Cadastro manual pelo dashboard.

Importação em lote a partir de pasta de fotos.

Importação a partir de link/pasta do Google Drive.

Cadastro por WhatsApp com foto(s), texto e/ou link de Drive.

Futuro suporte a Telegram/API sem reescrever o núcleo do sistema.

IA identifica o tema e variações, mas pergunta quando houver ambiguidade relevante.

Após cadastrar, a IA informa o resultado e permite correção.

Agenda mensal, semanal e diária.

Reserva deve respeitar o período completo entre retirada e devolução.

Conflitos de estoque devem bloquear a reserva e gerar alerta para avaliação humana.

Agenda sincronizada com Google Calendar.

Controle operacional apenas de reserva, locação, devolução e alerta de conflito na primeira versão; etapas de entrega/montagem etc. não serão obrigatórias.

Catálogo público funciona como portfólio, sem expor disponibilidade interna.

Botão de interesse direcionando ao WhatsApp.

Compartilhamento direto de um tema específico por URL.

Funcionários com níveis de acesso e permissões distintas.

Dashboard com indicadores e exportação de relatórios.

Arquitetura preparada para futuro SaaS multiempresa.

4. Arquitetura de solução recomendada

CLIENTES / EQUIPE       |       +--&gt; Catálogo público / Dashboard web       |            |       |            +--&gt; Supabase Auth       |            +--&gt; Supabase REST/SDK       |       +--&gt; WhatsApp Cloud API --&gt; n8n --&gt; Agente multimodal --&gt; API interna       |                                   |       |                                   +--&gt; Supabase DB/Storage       |       +--&gt; Google Drive --&gt; n8n --&gt; fila de importação --&gt; IA --&gt; Supabase       |       +--&gt; Google Calendar &lt;--&gt; n8n/API &lt;--&gt; reservas no SupabaseFONTE DE VERDADE: Supabase/PostgreSQLAUTOMAÇÃO: n8nARQUIVOS: Supabase StorageCALENDÁRIO: Google Calendar como integração/espelho, não como estoque principal

Supabase: a documentação atual posiciona Postgres como núcleo do projeto, com Auth, Storage, Realtime e Functions integrados. Storage usa metadados em Postgres, mas os objetos devem ser manipulados via Storage API, não editando diretamente o schema de storage. RLS deve ser aplicado às tabelas expostas. [R1-R4]

5. Arquivos e imagens

Preservar o arquivo original exatamente como recebido, sem sobrescrever o original.

Gerar versões derivadas somente quando necessário para performance do dashboard/catalogo.

Guardar metadados: nome original, MIME, tamanho, dimensão, checksum/fingerprint, caminho no Storage e entidade relacionada.

Usar foto principal + galeria ordenável por tema/variação/item.

Evitar guardar binários dentro do PostgreSQL.

Usar o Storage API para upload, move, delete e políticas de acesso. [R3]

6. Agente de IA: comportamento esperado

O agente deve ser tratado como um operador com ferramentas controladas, e não como um modelo com permissão irrestrita para escrever no banco.

6.1 Fluxo de foto pelo WhatsApp

Receber webhook de mensagem de mídia.

Identificar remetente autorizado (e/ou perfil de operador).

Baixar a mídia para armazenamento próprio imediatamente; URLs de mídia da WhatsApp Cloud API expiram após 5 minutos. [R5-R7]

Calcular fingerprint para evitar duplicação acidental.

Consultar temas/variações existentes para tentar encontrar correspondência.

Analisar a imagem com modelo multimodal.

Produzir saída estruturada com nome principal, possível variação, categoria, personagens, descrição, observações, itens visíveis e confiança.

Se houver certeza suficiente: criar ou atualizar o cadastro de acordo com regras de duplicidade.

Se houver ambiguidade: não inventar; perguntar com opções curtas.

Responder no WhatsApp com resumo do que foi feito e permitir correções.

Registrar a execução da IA e a decisão humana no log.

6.2 Exemplo de resposta da IA

✅ Cadastro realizadoMF-0127 - VingadoresVariação: Vingadores BabyCategoria: Super-heróisFotos adicionadas: 4⚠️ Não consegui confirmar se a variação é "Baby" ou "Kids".1 - Vingadores Baby2 - Vingadores KidsResponda 1 ou 2.

6.3 Regras de duplicidade

Se o tema já existir e a nova foto for do mesmo tema, perguntar se deve adicionar à galeria existente.

Se houver correspondência provável com variação existente, sugerir atualização da variação em vez de criar novo tema.

Nunca criar múltiplos cadastros só porque recebeu várias fotos do mesmo produto.

Usar fingerprint/hash para detectar o mesmo arquivo repetido.

8. Google Drive

A API do Google Drive permite listar arquivos/pastas e baixar arquivos blob usando files.get com alt=media. Portanto, o requisito de colar um link de pasta e importar suas imagens é viável; o sistema deve transformar o link em fileId, listar os descendentes e baixar apenas os tipos suportados. [R8-R9]

Preferir OAuth com escopo mínimo necessário.

Registrar drive_file_id, nome, MIME, pasta de origem e data da importação.

Impedir reimportação do mesmo arquivo quando a mesma pasta for enviada novamente, salvo ação explícita do usuário.

9. Agenda, locações e disponibilidade

A disponibilidade deve ser calculada pelo estoque interno. O Google Calendar será uma integração operacional para visualização e sincronização, não o banco de inventário.

9.1 Regra de conflito

Uma reserva deve comprometer o estoque no intervalo completo entre retirada e devolução, conforme a política operacional definida. Antes de confirmar a reserva, o sistema consulta locações ativas e quantidade física disponível.

disponivel = estoque_total - quantidade_comprometida_no_intervalo

Se disponível &gt;= quantidade solicitada: permitir.

Se disponível &lt; quantidade solicitada: bloquear a confirmação e exibir conflito.

O usuário pode abrir o conflito e avaliar a situação antes de prosseguir por uma ação administrativa explícita.

9.2 Google Calendar

A API do Google Calendar suporta criação, listagem, atualização e monitoramento de eventos, além do endpoint FreeBusy para retornar intervalos ocupados. As cotas atuais informadas pelo Google são 10.000 requisições/minuto por projeto e 600/minuto por usuário/projeto para Calendar; o uso padrão está sem custo adicional dentro das regras vigentes em 2026. [R10-R12]

Ao criar reserva: criar/atualizar evento e salvar external_event_id.

Ao editar reserva: atualizar o evento associado.

Ao cancelar: cancelar/apagar evento conforme política.

Se a sincronização externa falhar, manter a reserva interna e colocar sync_status=error; nunca perder a reserva por falha do Calendar.

13. Preparação para virar SaaS

Adicionar tenant_id em todos os registros operacionais.

Separar configurações por empresa: marca, domínio, categorias, regras e integrações.

Isolar dados por RLS.

Não colocar IDs ou secrets de uma empresa em código estático.

Criar slug/URL pública por empresa no futuro, por exemplo /maria-festeira ou subdomínio.

Manter arquitetura de integrações desacoplada: WhatsApp, Telegram e futuros canais devem chamar serviços internos comuns.

15. Critérios de aceite essenciais

Cadastrar manualmente Vingadores com 4 fotos e uma variação.

Adicionar mais 2 fotos ao mesmo tema sem criar duplicata indevida.

Cadastrar Kit Prata e vincular itens ao kit.

Cadastrar uma cômoda como item avulso e utilizá-la em dois temas distintos.

Ter estoque 2 para um tema e permitir 2 reservas sobrepostas no mesmo intervalo.

Tentar uma terceira reserva e receber conflito/alerta sem confirmação automática.

Criar uma reserva e sincronizar evento no Google Calendar.

Editar a reserva e refletir a alteração no evento externo.

Enviar foto pelo WhatsApp e ter mídia armazenada antes da análise expirar.

Enviar várias fotos do mesmo tema e obter um único agrupamento.

Enviar foto ambígua e receber pergunta de confirmação.

Mandar link do Google Drive e importar imagens da pasta.

Reimportar a mesma pasta e evitar duplicatas.

Compartilhar um tema pelo catálogo e abrir sua página pública diretamente.

Clicar no botão de WhatsApp e abrir conversa com contexto do tema.

Funcionário sem permissão de administrador não consegue alterar configurações críticas.

Gerar/exportar relatório operacional sem expor secrets ou dados de outros tenants.

17. Decisões técnicas fechadas

Supabase/PostgreSQL é a fonte central de verdade.

Supabase Storage é o armazenamento oficial das imagens do catálogo.

n8n é a camada de orquestração, não a base do inventário.

Google Calendar é sincronização/visualização; disponibilidade real é calculada no banco interno.

WhatsApp Cloud API será o canal inicial do agente.

Google Drive será fonte de importação, não o repositório definitivo das imagens.

Agente usa ferramentas explícitas para ler/criar/editar dados.

Ações de alto impacto e ambiguidades relevantes pedem confirmação humana.

O schema nasce multi-tenant, mas com Magia Festeira como único tenant inicial.

O dashboard e o catálogo público compartilham a mesma base, mas têm autenticação, permissões e superfícies diferentes.
